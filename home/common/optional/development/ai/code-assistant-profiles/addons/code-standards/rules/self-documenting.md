Code documents itself to the core: open any file cold and within seconds know what it is for and how it fits, without the chat, the commit or the author. Names and structure carry what they can; comments carry what they cannot: why, constraints, and the contract a name can't hold (see the comments rule). This rule owns the shape; choosing the words is the domain-language-steward skill's job: load it when a name is in doubt.

- **One concern per file or package, named for that concern.** `rates.ts`, `label-printing.py`, not a `utils` or `helpers` file whose contents share no purpose. Where the package is the unit (Go), split files as they grow, not before. Conventional entry points (`main.go`, `index.ts`, `default.nix`, `mod.rs`) keep their names and stay thin.
- **Place by meaning, never by convenience.** Code goes beside the code it changes with, not where a variable it needs happened to be in scope. Edits that keep crossing a module boundary mean the boundary is wrong. This binds code the change adds; moving existing code is its own step, with its own reason.
- **Entry points read as a story.** A top-level function is a short list of steps named by intent (`loadConfig`, `quoteRates`, `printLabel`), each step's detail one call down. Extract a step when working out what it does takes effort, and only if it reads without its caller; one-liners and code you must read together stay inline.
- **Group by concept, not by kind;** layers inside one concept are fine. Settings sit under what they configure (`shipping.cutoffTime`, not `config.shippingCutoffTime`). Unit tests sit beside the concern they prove, the way the language does it; tests spanning concerns go in the toolchain's tests directory.
- **Name the choice, not a bool.** If a boolean picks which behaviour runs, give each behaviour its own operation (`holdShipment`/`releaseShipment`) or pass an enum; a named argument only fixes the call site. A boolean that is plain data, like `isResidential`, is fine.
- **Declare, don't assemble.** Prefer a form where the contract reads in one place: a schema or typed options over hand-checked maps.
- **The test for it:** someone who has never seen the repo opens the file and can say what it is for in one sentence. If they couldn't for a file this change creates or reshapes, restructure before calling it done.
